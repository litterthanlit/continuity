# 0003 — MCP server: a router over child `ct` processes

**Status:** accepted · 2026-10-08

## Context

The Claude Code plugin gives Claude Code agents the studio via `npx ct` + Bash.
Agents in other clients (Cursor, Codex, VS Code, Claude Desktop, chat-only apps)
need the same gate, eyes and bookkeeping as MCP tools — ideally with images inline,
since "read the PNG" is the whole point of the eyes.

## Decisions

### 1. Every operation runs in a fresh child process
`ct mcp` (stdio, `@modelcontextprotocol/server` v2, Apache-2.0) is a router. Each tool
spawns `node bin/ct.mjs <command>` with `CT_ROOT` and `CT_RESULT_FILE`. An in-process
server was rejected because:

- Node's ESM cache never evicts: a long-lived process would build **stale scenes**
  after edits (and cache-busting the scene URL misses relative `lib/` imports), while
  `sourceHash` reads the new files — gate results would be recorded against code
  they didn't test.
- `WORK_ROOT` is fixed at import, the kit's active-scene state races across concurrent
  builds, and the state lock spins with `Atomics.wait` (would stall the transport).
- Commands print to stdout, which the stdio transport owns.

Cost: ~1s of startup per call, negligible next to builds and browser work. Benefits:
crash isolation, cancellation (kill the child), and reuse of the cross-process
browser semaphore, so parallel tool calls queue for Chrome correctly. Operations on
the same project are additionally serialized in the server (a build rewrites
`build/<slug>`).

### 2. Results protocol
`emitResult()` (`src/cli/lib/result.ts`) shallow-merges structured data into
`$CT_RESULT_FILE`. Every command emits what it already computed (findings + counts,
iteration, image paths, render info, scores…). The human log is unchanged, so the
terminal UX and the MCP data come from the same run. Tool results carry the summary +
trimmed log as text, images as `image` blocks, and the result as `structuredContent`.
Gate failures are data (`ok: false`); `isError` is reserved for crashes and usage errors.

### 3. Images
Sheets, packs, strips and motion charts are already ≤ 1568px wide; stills are
downscaled with sharp to a 1568px long edge. At most 12 images per call; the rest are
listed by path.

### 4. Workspace root, not per-call paths
The repo is `$CT_ROOT`, else the client's first MCP root (2025-era clients; `roots/list`
is deprecated in the 2026-07-28 revision), else the server's cwd. No tool takes a path
outside a project, so a model can't point the server at arbitrary directories.

### 5. Sandboxed project files
For clients without file tools, `read/write/list_project_files` reach only a project's
sources: `brief.md`, `treatment.md`, `storyboard.json`, `theme.ts`, `scenes/<id>.tsx`,
`lib/**/*.ts(x)|json`, and text assets. No `..`, no absolute paths, symlinks may not
lead out of the project (checked on the deepest existing ancestor), ≤ 512 KB, text only.
Code/storyboard writes run `lint --fast` and return its findings — the MCP twin of the
Claude Code edit hook.

### 6. Knowledge travels with the package
`plugin/skills` ships in the npm package and is served as `continuity://guide/...`
resources, each prefixed with a CLI → tool mapping. The `make-video` and `review`
prompts restate the director/builder/critic workflow for a single agent driving tools.

### 7. Not wired into the Claude Code plugin
Claude Code already has the CLI; a second surface would add ~22 tools to context for
no new capability. `claude mcp add` is documented for anyone who wants it.

## Verification
`tests/mcp.test.ts` drives the server over stdio with the official client (tools,
init → new → lint, sandbox refusals, lint-on-write, resources, prompts; with
`CT_SLOW=1`: check, image blocks ≤ 1568px, draft render). `scripts/pack-smoke.mjs`
handshakes with the server from the installed tarball under npm and strict pnpm. A
headless Claude Code session configured with the server described the contents of a
returned contact sheet correctly.
